# Нагрузка и задержка

## Быстрый замер gateway

`make load` и `./scripts/dev.ps1 load` проверяют цепочку HTTP → gateway → risk → commit в PostgreSQL на выделенном стенде. По умолчанию генератор отправляет только синтетическую проверку `demo-clean` на `127.0.0.1:18080`. Каждый запрос открывает новое соединение. [Профиль](gateway-profile.json) задаёт 5 с разогрева, 15 с при 10 запросах/с, 15 с при 100 запросах/с и 10 с восстановления при 10 запросах/с. Разогрев публикуется отдельно. Он не входит в оценку бюджета.

Из корня репозитория запусти стенд с отдельным именем Compose и свежим volume. Используй новое имя для каждого замера. Для сравнения собирай сервер на соответствующем коммите, оставляя одну версию генератора и профиля.

```sh
export GATEWAY_HOST_PORT=18080 POSTGRES_HOST_PORT=55434
docker compose -p antifraud-load-base up --build -d --wait
python scripts/load.py --server-ref "$(git rev-parse HEAD)" --output .local/load-base
docker compose -p antifraud-load-base down
```

```powershell
$env:GATEWAY_HOST_PORT = '18080'
$env:POSTGRES_HOST_PORT = '55434'
docker compose -p antifraud-load-base up --build -d --wait
./scripts/dev.ps1 load -ServerRef (git rev-parse HEAD) -Output .local/load-base
docker compose -p antifraud-load-base down
```

`down` сохраняет volume. Если запускаешь сервисы вручную, используй ту же топологию, свежую выделенную БД, сборщик `-once` и gateway на `127.0.0.1:18080`. `--port` позволяет указать другой локальный порт. Значение `--server-ref` — SHA или идентификатор сборки **работающего сервера**. Без него результат можно изучать, для сравнения оба отчёта должны указывать версию сервера.

Для кандидата повтори тот же запуск на отдельном экземпляре, например `antifraud-load-candidate`. Передай базовый отчёт и новый каталог результата.

```sh
python scripts/load.py --server-ref "$(git rev-parse HEAD)" --baseline .local/load-base/metrics.json --output .local/load-candidate
```

```powershell
./scripts/dev.ps1 load -ServerRef (git rev-parse HEAD) -Baseline .local/load-base/metrics.json -Output .local/load-candidate
```

Сравнение сверяет профиль, генератор, его окружение и начальные счётчики истории. Дополнительно зафиксируй конфигурацию сервера, CPU, RAM, диск и версии инструментов. Одинаковые счётчики истории сами по себе не гарантируют одинаковые данные. В каталоге результата есть таблица `metrics.md`, агрегаты `metrics.json` и наблюдения по отправленным запросам `samples.jsonl`. `--check` или `-CheckBudget` возвращает ошибку при выходе за бюджет профиля после сохранения отчёта. Бюджет этого опыта — p99 до 200 мс, ноль ошибок и пропусков для измеряемых фаз. Он относится к пилоту на выделенном стенде. Обычный PR CI не оценивает скорость на общих раннерах.

## Как оценить скорость самим

1. **Проверь, достигнута ли нагрузка.** `offered_rps` — сколько запросов запланировано. `started_rps` — сколько отправлено по расписанию. `goodput_rps` — сколько из запросов этой фазы успешно завершилось до её конца за секунду. Завершения после границы показаны отдельно. `dropped` означает, что запрос не был отправлен. `generator_late` указывает на опоздание генератора, `in_flight_limit` — на исчерпание лимита одновременных запросов. При любом пропуске уточни достижимую скорость по факту.
2. **Читай хвост вместе с ошибками.** p99 по правилу ближайшего ранга — задержка ответа на позиции `ceil(0,99 × N)` в отсортированном списке успешных проверок. p50 отражает типичный запрос, p95 и p99 — хвост, max — худший наблюдавшийся успешный запрос. Отдельно оцени `failed`, `timeouts`, коды HTTP и долю пропусков. Например, шлюз может вернуть HTTP 503 раньше клиентского таймаута. Падение p99 при росте ошибок само по себе не свидетельствует об ускорении.
3. **Найди границу пропускной способности.** На выделенном стенде повтори измерение при нескольких ступенях заданного RPS. Измени только `requests_per_second` в копии профиля и передай `--profile`. Для каждой ступени сохрани p99, `goodput_rps`, ошибки и пропуски. Наибольшая ступень, где подтверждается заданная скорость и соблюдается бюджет, даёт нижнюю оценку устойчивой ёмкости для этого профиля. На коротких фазах оценка предварительная. При 100 запросах/с и средней задержке 50 мс при устойчивой нагрузке ожидается около пяти одновременных запросов. Используй это как ориентир для выбора числа воркеров генератора.
4. **Повтори базу и кандидат.** Для небольших дельт сделай по три прогона с одинаковой подготовкой и сравни разброс p99 каждой фазы. Если p99 растёт при стабильной скорости отправки, проверь нагрузку CPU, диск, ожидание пула и блокировки `account_guard`. Если `goodput_rps` падает одновременно с пропусками, сначала выясни, ограничивает ли прогон генератор. Зафиксируй вывод по данным, а затем проверь корректность `make e2e`.

## Профиль приёмки ADR-007

Машиночитаемый профиль — profile.json. Цель p99≤200мс измеряется клиентом на полном HTTP gateway→risk→БД→commit пути, без ожидания пользователя. HTTP timeout 1.5с — граница отказа, не доказательство p99. Исполнение outbox измеряется отдельно.

Порядок: развернуть P/S1/S2/A с конфигурацией ADR; зафиксировать CPU/RAM/диски/ОС/версии, настройки WAL/pool/репликации/индексы, размер evidence, аккаунты и skew. Подготовить до 100000 активных аккаунтов, полную 90-дневную историю (8.64 млн событий/день при 100/с; ~1.56ТБ полезных событий до индексов), 30д регистраций и размер годовой истории решений. Скрипт подготовки объёма и обобщённый входящий event API ещё требуют реализации; локальные три аккаунта не представляют этот объём.

После 60с разогрева 30мин одновременно: входящие события 100/с, проверки 10/с, регистрации 1000/с. Затем без остановки всех потоков 10мин: события 1000/с, проверки 100/с, регистрации 1000/с (предварительно, уточнить у оператора). Вернуться к steady и измерить восстановление очередей. Рандомизация по фиксированному seed; отдельные группы low/medium/high, unknown, late и duplicate. Challenge-ожидание исключается, но сохранение step_up включается.

checks.js — воспроизводимая часть профиля для проверок: `k6 run --summary-export .local/k6-summary.json docs/load/checks.js` на свежем демо со сборщиком. Она создаёт protected checks по требуемому расписанию, но использует один hot account. Без двух других потоков и prefill это только smoke, не полная проверка ADR. k6 не подключается как скрытая внешняя зависимость навыков. Зафиксировать версию k6 перед запуском в манифесте прогона.

Полный прогон должен публиковать p50/p95/p99/max, ошибки/timeout/dropped iterations, фактическую скорость каждого потока, lag ingest и outbox, блокировки/повторы, WAL/fsync, CPU/IO/RAM/диски и lag A. Сохранить сырые histogram/JSON, commit и конфигурацию. Совместить расследование (≤5с), прогон правил 90д (≤1ч) и lag A≤5мин. Не выдавать среднее время или низкую нагрузку за p99 целевого контура.

HA-серия отдельно: потеря каждого P/S1/S2, разделение сети, неизвестный исход COMMIT, возврат старого P, восстановление backup+WAL. Проверить RPO=0, RTO≤5мин, fencing и отсутствие двойного лидера. Из одного локального PostgreSQL это не выводится. Реальные Play Integrity/ключи, ресурсные бюджеты и экран подтверждения требуют физического Android-устройства.

Результаты выполненных локальных проверок — ../verification.md. Полная нагрузочная приёмка и HA пока не проводились.
