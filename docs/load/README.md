# Будущий совместный прогон ADR-007

Машиночитаемый профиль — profile.json. Цель p99≤200мс измеряется клиентом на полном HTTP gateway→risk→БД→commit пути, без ожидания пользователя. HTTP timeout 1.5с — граница отказа, не доказательство p99. Исполнение outbox измеряется отдельно.

Порядок: развернуть P/S1/S2/A с конфигурацией ADR; зафиксировать CPU/RAM/диски/ОС/версии, настройки WAL/pool/репликации/индексы, размер evidence, аккаунты и skew. Подготовить до 100000 активных аккаунтов, полную 90-дневную историю (8.64 млн событий/день при 100/с; ~1.56ТБ полезных событий до индексов), 30д регистраций и размер годовой истории решений. Скрипт подготовки объёма и обобщённый входящий event API ещё требуют реализации; локальные три аккаунта не представляют этот объём.

После 60с разогрева 30мин одновременно: входящие события 100/с, проверки 10/с, регистрации 1000/с. Затем без остановки всех потоков 10мин: события 1000/с, проверки 100/с, регистрации 1000/с (предварительно, уточнить у оператора). Вернуться к steady и измерить восстановление очередей. Рандомизация по фиксированному seed; отдельные группы low/medium/high, unknown, late и duplicate. Challenge-ожидание исключается, но сохранение step_up включается.

checks.js — воспроизводимая часть профиля для проверок: `k6 run --summary-export .local/k6-summary.json docs/load/checks.js` на свежем демо со сборщиком. Она создаёт protected checks по требуемому расписанию, но использует один hot account. Без двух других потоков и prefill это только smoke, не полная проверка ADR. k6 не подключается как скрытая внешняя зависимость навыков. Зафиксировать версию k6 перед запуском в манифесте прогона.

Полный прогон должен публиковать p50/p95/p99/max, ошибки/timeout/dropped iterations, фактическую скорость каждого потока, lag ingest и outbox, блокировки/повторы, WAL/fsync, CPU/IO/RAM/диски и lag A. Сохранить сырые histogram/JSON, commit и конфигурацию. Совместить расследование (≤5с), прогон правил 90д (≤1ч) и lag A≤5мин. Не выдавать среднее время или низкую нагрузку за p99 целевого контура.

HA-серия отдельно: потеря каждого P/S1/S2, разделение сети, неизвестный исход COMMIT, возврат старого P, восстановление backup+WAL. Проверить RPO=0, RTO≤5мин, fencing и отсутствие двойного лидера. Из одного локального PostgreSQL это не выводится. Реальные Play Integrity/ключи, ресурсные бюджеты и экран подтверждения требуют физического Android-устройства.

Результаты выполненных локальных проверок — ../verification.md. Полная нагрузочная приёмка и HA пока не проводились.
