# История метрик релизов

## Запуск для команды

1. После слияния workflow в основную ветку запушь реальный Git-тег на SHA кандидата. Создай черновик GitHub Release с этим существующим тегом. Сохрани его как черновик до окончания проверки.
2. В **Actions → release metrics → Run workflow** выбери основную ветку и передай `tag`. По умолчанию база — последний опубликованный стабильный релиз. `baseline_tag` позволяет выбрать другой опубликованный тег. Для первого релиза сравнение получает `UNVERIFIED`.
3. Открой сводку Actions и файлы черновика. Просмотри статус E2E, политику и результаты каждого нагрузочного повтора, затем принимай решение о публикации.

После появления workflow в основной ветке тот же запуск доступен из CLI:

```sh
gh workflow run release-metrics.yml --ref main -f tag=v0.1.0
```

В черновик добавляются два файла. `release-metrics.md` содержит исходы политики, заданные и достигнутые запросы/с, p95/p99, ошибки, таймауты и пропуски по фазам и повторам. В нём видны диапазон p99 и дельты. `release-evidence.zip` содержит SHA обоих серверов, версию инструментов, конфигурацию Compose, сведения о раннере, все агрегаты и сырые наблюдения.

## Как считать дельту

Workflow проверяет выбранный тег, собирает сервер из его файлов и прогоняет `make e2e`, фиксированную оценку политики без фона и при всплеске, а также три нагрузочных повтора. Отчёт о всплеске показывает, какие исходы изменились относительно прогона без фона на том же SHA. Для каждого повтора используется свежая синтетическая PostgreSQL. Предыдущий релиз повторно измеряется на том же раннере и тем же измерителем. Его первоначальный отчёт остаётся у прежнего релиза. Дельта нагрузки — медиана повторов кандидата минус медиана повторов базы. Для политики сравниваются счётчики при совпадении набора и измерителя.

Сопоставимость нагрузки требует полных серий с одинаковым профилем, генератором, окружением и начальными счётчиками истории. Старый тег может не поддерживать отдельные порты или текущий контракт. При отсутствии сопоставимых данных дельта имеет статус `UNVERIFIED`. `FAIL` у бюджета пилота означает наблюдавшееся превышение хотя бы в одном повторе. GitHub-hosted раннер подходит для парных пилотных замеров. Для приёмки по ADR‑007 нужны [совместный профиль и стабильный стенд](load/README.md#профиль-приёмки-adr-007).

Измерение выполняется с правами чтения. Записывающий job сверяет фактический SHA тега с отчётом и ищет черновик. Уже прикреплённые файлы сохраняются. Для повторного запуска упавшего job `attach` используй **Re-run failed jobs**, чтобы переиспользовать тот же архив. Если в черновике уже есть одноимённые файлы с другими контрольными суммами, workflow остановится и оставит их для проверки команды.
